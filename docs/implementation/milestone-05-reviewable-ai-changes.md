## Approved 2026-08-27 redesign — authoritative

Hosted testing proved the multi-object AI edit path but also showed that the original per-object approval and guided-story workflow exposed implementation detail and required too much ceremony for normal canvas work. The product owner approved replacing that first-version interaction with a conversational, transaction-based model. This section and master-plan decision `PD-012` supersede the conflicting interaction, review-panel, story, decision, and exit-criteria language retained later in this document as implementation history.

### Revised goal and user-visible outcome

An owner or editor using the user-facing **Edit with undo** authority can ask the primary AI for a change from a normal canvas comment. The AI applies the validated result immediately as one durable canvas transaction and replies with a concise description of what visibly changed. The reply never exposes UUIDs, domain command names, staging terminology, provider structure, or database state.

The AI turn participates in ordinary canvas history as one unit. When it is the latest undoable action, the canvas Undo command and `Cmd/Ctrl+Z` roll back the whole turn. The AI reply also exposes one unobtrusive **Undo AI change** action so the user can deliberately roll back that transaction later; the server restores only the AI-owned fields that still match its recorded after-state and preserves unrelated later human changes. A same-field conflict fails visibly instead of overwriting the later human value.

Revision is conversational. A user replies naturally in the same thread—for example, “make them smaller” or “arrange them vertically”—and inherited AI recipient context starts another bounded run against current authorized canvas state. There is no Request revision mode, per-object Keep or Discard, guided framing, Previous/Next workflow, or explicit acceptance step. Leaving the result in place, closing the thread, continuing work, or changing the topic simply leaves the durable transaction intact.

The existing change-set and per-object before/after records remain internal safety, audit, idempotency, and rollback metadata. They are not rendered as product copy. The internal `edit_with_review` identifier remains stable for compatibility while its user-facing label becomes **Edit with undo**.

### Revised requirements and acceptance

- **FR-067 — Plain-language AI change summary.** Describe visible outcomes only; never render object UUIDs, command names, staging status, or raw tool output.
- **FR-068 — Atomic AI-turn undo.** Apply and roll back one AI turn as one conflict-safe transaction while preserving unrelated later work.
- **FR-069 — Conversational revision.** Use ordinary replies in the originating comment thread for modifications; preserve server-derived scope and current authorization.
- **FR-070 — Implicit acceptance.** Require no Keep action and no pending-review cleanup decision.
- **FR-071 — Optional affected-object inspection.** If exposed, highlight the complete affected set without guided navigation or required decisions.
- **AS-006 — Conversational AI edit with undo.** On one authenticated immutable preview, a multi-object AI edit produces plain-language copy and an immediately durable result; a normal reply revises it; Undo restores the prior state as one operation while an unrelated later human edit remains; leaving another result alone requires no acceptance action.
- The original `FR-031` through `FR-035` and `AS-002` / `AS-005` remain verbatim in the master ledger only for source traceability and are not first-version exit requirements after `PD-012`.
- Semantic projection, deterministic layout, transient visual feedback, scope enforcement, authorization, idempotency, collaboration, and deterministic visual-quality boundaries remain unchanged.

### Revised technical approach

- Keep provider and server tool contracts structured, but construct the persisted user-facing reply from the provider's plain-language body plus a bounded product summary. Do not append `ValidatedCanvasReviewStage.summary`, command lines, affected IDs, or activation instructions.
- Continue validating and activating the entire change set through the trusted server path. Treat activation as the durable completion of the user-visible AI transaction rather than the start of a pending approval session.
- Add one authorized change-set undo operation that builds a single compensating Yjs update from the complete affected set, records an idempotent terminal undo outcome, appends one durable sequence, and broadcasts it once. Preserve affected-field conflict checks and full-state guards for created/deleted objects.
- Make the latest AI transaction available to the invoking actor's normal canvas Undo stack as one entry. Keep the reply-level Undo action for discoverability and selective later rollback; both paths call the same server-authorized transaction undo boundary.
- Remove Review changes entry points, review-panel rendering, guided story generation/playback, Keep/Discard/Request revision controls, and pause/resume framing from the first-version UI. Retain dormant historical schema only where removing it would create migration risk; do not create new review stories or per-object human decisions.
- Reuse inherited comment recipient context for conversational revisions. A normal reply addressed to the AI starts a new run; it does not first restore the prior transaction unless the user explicitly asks to undo it.

### Approved 2026-08-28 prompt-robustness hardening

Hands-on preview testing repeatedly found defects with plausible prompts that were not represented by the deterministic fake-provider browser suite. The product owner approved one additional Milestone 5 hardening pass before closure. It does not broaden the canvas feature set or imply arbitrary AI manipulation; it makes the current supported capability boundary measurable and requires unsupported requests to fail safely.

1. **Semantic prompt corpus:** define 30 synthetic edit prompts across ten supported or deliberately unsupported intents, with three materially different phrasings per intent. Keep expected tools, scope, object counts, layout operations, and safe-refusal behavior machine-readable.
2. **Live-provider evaluation:** run the corpus through the same strict OpenAI gateway and authority-derived tool schema used by the product. Use synthetic canvas content only, `store: false`, one request at a time, a 75-second deadline, privacy-safe incremental observations, bounded token output, and three repetitions by default.
3. **Reliability and safety gates:** require 100% of critical creation, connector, direct-scope, unsupported-request, and timeout cases; at least 95% overall; no response beyond the deadline; no unknown or out-of-scope tool; no technical identifiers in visible reply copy; and no duplicate fixture/repetition observation.
4. **Regression conversion and exploratory acceptance:** retain deterministic browser coverage for every hosted defect, add structural evaluator tests for paraphrase coverage and threshold enforcement, and reserve product-owner testing for fresh prompts not copied from the corpus. A safe, explicit refusal is acceptable for unsupported work; a hang, false success claim, unsafe partial mutation, duplicate effect, or scope violation is not.

Live-provider evaluation is evidence for model/tool selection, not proof that canvas persistence, vision refinement, or undo completed. Exact-head CI, immutable-preview application testing, visual inspection, reload, collaboration, and atomic undo remain separate required evidence.

### Approved 2026-08-28 acceptance-reliability slices

Fresh exploratory testing found a repeat-after-undo failure and two comment-surface interruptions after the prompt corpus passed. The product owner approved completing the following slices before another hands-on preview:

4. **Provider resilience and layout staging:** allow one bounded automatic provider retry before any canvas mutation, reserve the worst-case attempt budget, retain privacy-safe attempt metadata, and normalize deterministic layout explanations to the objects that actually changed.
5. **Regression and replacement preview:** add database, unit, and full browser coverage for these paths; run the complete exact-head quality and database gates; then commit, push, obtain protected CI, apply only the new preview migration, and publish a matching immutable preview for product-owner testing.

## Historical 2026-08-26 plan — superseded interaction model

### Goal and user-visible outcome

Turn Milestone 4's protected `edit_with_review` staging records into a complete, object-by-object review workflow without adding another AI conversation surface or weakening the shared canvas command, persistence, and permission boundaries.

When this milestone is complete, an owner or editor can ask the primary AI for an edit from an existing comment thread, open the resulting review from that same thread, and see the proposed changes tentatively on the shared canvas. Every added, edited, or deleted object has its own plain-language explanation of what changed and why. A generated review story frames one affected area at a time in deterministic order, keeps the explanation and currently valid actions visible, and allows the reviewer to keep, request revision of, or discard each object independently.

The originating comment's target defines the mutation envelope. A comment anchored directly to one object may produce reviewable changes only to that object. A world-space comment placed on blank canvas may produce one coordinated change set that adds, edits, or deletes multiple grounded objects, and that same comment thread owns the review of all changes in the set. Nearby objects may inform the AI's interpretation, but proximity alone neither includes nor excludes an object.

For visually sensitive requests, the AI receives complete semantic style/layout state plus bounded before-and-after render captures of the authorized target region. It uses a small set of deterministic layout tools for alignment, distribution, spacing normalization, and resize-to-content before a staged result reaches human review. Structured object state and stable IDs remain authoritative; screenshots improve visual judgment but never grant scope or mutation authority.

Keep leaves that object's reviewed state on the canvas. Discard immediately restores only the AI-owned fields or object state recorded before the change, preserving unrelated later human work. Request revision records the reviewer's direction and returns the replacement request to the originating comment conversation under the approved revision lifecycle. Two authenticated sessions see the same tentative changes, review decisions, progress, and final durable canvas after reload.

Milestone 5 is a bounded review experience. It reuses the existing shared panel system and the existing `stories` / `story_scenes` foundation for a review-specific story. It does not create a dedicated AI chatbot, a general story editor, narration, branching, first-class documents, annotations, voice, or the later Milestone 8 guided-story product.

## Requirements covered

This plan covers these exact Milestone 5 product requirements from the master ledger:

- **FR-031 — Explanation per reviewed object.** In edit-with-review mode, every added or edited object receives an attached explanation of what changed and why.
- **FR-032 — Review actions.** The user can keep, request revision of, or discard each reviewed AI change independently.
- **FR-033 — Immediate restoration.** Discard restores the affected content to its prior state immediately without reverting unrelated later work.
- **FR-034 — Guided review story.** The product can generate and play a review story that visits AI changes one at a time.
- **FR-035 — Contextual review step.** Each step frames the relevant change and exposes its explanation and currently valid actions.
- **AS-002 — Reviewable AI edit.** In edit-with-review mode, an AI label change receives an explanation; keep, revise, and discard are available; discard immediately restores the prior label.
- **AS-005 — Guided review.** A multi-change AI review story visits one affected area at a time and provides the correct review controls at each scene.
- **Exit gate:** “Complete the sourced **Reviewable AI edit** and **Guided review** acceptance scenarios, including a mixed keep/discard change set and a concurrent unrelated human edit.”
- **Visual-grounding supporting work:** complete semantic style/layout projection, bounded deterministic layout tools, targeted before/after vision feedback, and deterministic visual-quality checks added to the master ledger under Milestone 5 on 2026-08-26.
- **Visual-grounding exit evidence:** on the same immutable preview, visually sensitive single-object and world-space multi-object changes must prove grounded styling/layout, scope preservation, and reviewable results without clipping, unsafe overlap, invalid contrast, or persisted capture content.

The current Milestone 4 boundary already validates and stores pending `ai_change_sets` and `ai_object_changes` with full per-object before/after state and affected-field paths, but deliberately leaves canonical canvas state unchanged and exposes no review decisions or review UI. That staging boundary is an implementation prerequisite, not evidence that any Milestone 5 requirement is complete.

GitHub reports PR #9 merged on 2026-08-26 and post-merge `main` CI run [`32992538061`](https://github.com/jewilhel/Thinking-Canvas/actions/runs/32992538061) passed for that exact commit.

Do not alter any Milestone 4 completion checkbox as part of this draft.
- Preserve the Milestone 4 comments-only AI communication rule. The originating comment thread remains the place for the AI request, staging summary, revision request, provider progress, failure, and replacement response. The Review panel is an object-decision workflow, not another chat history.
- Before product code, re-read the installed Next.js 16.3 guidance under `node_modules/next/dist/docs/` for every affected Route Handler, data-security, mutation, streaming, and Server/Client boundary.

### Comment-defined mutation scope

- Derive the mutation envelope from the persisted source comment and its server-resolved target context before calling the provider. Never accept scope kind or allowed object IDs from the browser or provider.
- For a direct single-object anchor, accept the simulated result only when its affected-object set contains that exact object ID and no other ID. The AI may edit or delete the target object, but it may not create a new object or mutate a second object, including through reorder, group, or connector commands. A request that requires broader changes receives a readable scope-limit reply in the same comment thread and stages nothing.
- For a world-space comment placed on blank canvas, allow one validated change set to add, edit, or delete multiple objects on the same canvas. The originating comment thread remains the parent conversation and review entry for the complete set; each object still receives its own explanation and independent Keep, Request revision, or Discard decision.
- Preserve the existing bounded meaning of explicit group and ordered selected-path contexts: the simulated affected-object IDs must remain within the server-resolved context IDs. Derived rendering changes, such as a connector visually following an edited endpoint, are not separate mutations unless the connector itself appears in the validated change set.
- Treat visual proximity only as grounding evidence for the AI's interpretation. It does not automatically add nearby objects to the mutation envelope, and it does not permit cross-canvas access. If the user wants broader scope from a single-object thread, the AI explains that they should start a world-space comment or another explicitly bounded multi-object context.

### Semantic visual grounding and deterministic layout

- Version the AI projection to include the complete render-affecting state needed for visual reasoning: object-specific content, full style, geometry/rotation, group and stacking order, connector endpoints/relationships, computed text and object bounds, clipping/overflow state where available, alignment/spacing relationships, and applicable design tokens. Preserve the existing bounded-size and off-screen coverage rules.
- Add server-defined high-level layout tools for `align`, `distribute`, `normalize_spacing`, and `resize_to_content`. Each tool resolves its exact object IDs, computes deterministic commands, and passes through the same comment-defined scope, Zod validation, current authorization, Yjs simulation, idempotency, staging, collaboration, and reversal paths as direct product commands.
- Keep the initial tool set intentionally bounded. Grid/flow composition, reusable style presets, connector routing, and template-scale orchestration belong to the master ledger's Milestone 10 expansion unless separately promoted.
- Render transient captures from the trusted canvas renderer after loading the same authoritative state used for the projection. A direct-object request receives the target plus bounded surrounding context; a world-space request receives the grounded affected region plus a lower-resolution full-canvas orientation image. Do not send unrelated canvas regions merely because they are visible to the browser.
- For a visually sensitive staged change, render the simulated after-state without mutating the canonical canvas and run at most the approved bounded number of visual-feedback passes. Supply both semantic before/after diffs and labeled render context so the model critiques hierarchy, balance, whitespace, and visual coherence without guessing identities from pixels.
- Run deterministic visual-quality checks for text clipping, object overlap, minimum spacing, color contrast, canvas bounds, and connector integrity. A vision critique may request another validated tool pass, but it cannot waive a failed deterministic check, widen the mutation envelope, or directly generate a trusted update.
- Treat provider captures as ephemeral inputs: bound count, dimensions, bytes, token/cost estimates, timeout, and retry; use `store: false`; do not automatically write their image bytes or base64 data to relational records, application logs, evaluation traces, or review explanations. Retain only privacy-safe capture metadata and validation outcomes. Separately approved, minimized QA screenshots may still be retained as verification evidence under the existing milestone evidence rules.

### Review contract and per-object explanations

- Extend the `stage_canvas_changes` contract so the provider supplies exactly one structured explanation for every affected object: a concise `whatChanged` statement and a non-empty canvas-grounded `why`. Validate that the explanation object IDs exactly match the server-simulated affected-object set—no missing, duplicate, extra, stale, or cross-canvas IDs.
- Keep the server authoritative for before/after state and affected-field paths. The provider may explain a simulated result but may not supply trusted before images, after images, order indexes, actor IDs, command IDs, canvas IDs, or authorization metadata.
- Store structured explanation fields per `ai_object_changes` row while retaining the existing bounded `explanation` value as a backward-compatible display fallback for already-staged non-production records.
- Treat create, edit, reorder/group effects, and delete as reviewable staged state because the existing Milestone 4 tool accepts the full supported mutation vocabulary. For a newly added object, Discard removes it only if it still matches the tentative after-state. For a deleted object, the review step frames its recorded prior bounds and Discard restores it only when its identity/order position can be restored without overwriting later work.
- Reject activation when an object lacks a valid per-object explanation or when its before/after state cannot be parsed by the current versioned canvas schema. Never replace the last valid canvas with an incomplete review.

### Activation, independent decisions, and precise restoration

- Add a server-only review service and uncached authenticated Route Handlers for loading a review, activating it, deciding one object, requesting revision, and refreshing status. Browser requests carry stable IDs and idempotency keys, never trusted object snapshots or Yjs updates.
- On activation, re-authenticate the human, re-check current membership, load the latest durable snapshot plus updates, and compare each staged object's affected paths with its recorded before-state. Preserve unrelated current fields. Mark a same-field divergence as an explicit object-level conflict rather than overwriting it.
- Under the recommended tentative-application decision, apply all non-conflicting after-state paths as one AI-origin pending-review Yjs update. Persist the server-assigned sequence and activation metadata atomically with the change-set transition, then Broadcast the acknowledged sequence through the existing private canvas collaboration path.
- Make each object action independent. Keep records a terminal decision and emits no canvas update. Discard emits one field-aware compensating update only for paths still equal to the tentative after-state; unrelated later human fields remain untouched. Added-object Discard and deleted-object restoration use full-state identity/order guards.
- If a human changed the same AI-owned field after activation, fail the destructive portion closed and show the exact conflicting field. Do not claim `FR-033` for that conflict case; the required acceptance evidence must use an unrelated concurrent edit and prove immediate restoration. Provide a safe retry or explicit “keep current human value” resolution within the approved review action, not an automatic overwrite.
- Persist the review decision and any generated canvas update in one trusted transaction with current role, change-set status, object-change identity, expected durable sequence, decision idempotency, and one-terminal-outcome checks. Repeated requests return the original result; changed-content reuse fails.
- Derive change-set progress (`pending`, `applied`, `partially_reviewed`, `complete`, or `failed`) from activation and terminal object outcomes. A mixed set remains `partially_reviewed` until every object has Keep, Revise, or Discard; it becomes `complete` only when every object has a terminal outcome and no unresolved activation conflict remains.

### Revision through the existing comment conversation

- Link every change set to its originating `ai_run`, root comment, accountable requester, and optional parent object change. Do not create review-specific chat messages.
- Under the recommended revision decision, require a bounded non-empty revision note. Atomically record the object decision and conflict-safe restoration, then create exactly one child run addressed to the primary AI in the same open originating thread.
- Scope the child run to the current durable object, the original per-object explanation, the reviewer's note, and relevant thread history. Re-check current `edit_with_review` authority before provider access and again before staging the replacement.
- A replacement stage creates a new linked change set/object change; it never rewrites the original before/after evidence or decision. Cancellation, timeout, budget, retry, prompt-injection, and provider audit behavior reuse Milestone 4's existing inline run boundary.
- If the source comment is no longer open, authority was downgraded, membership was removed, or the object no longer exists when revision begins, record a readable failure and leave restored canvas content untouched.

### Guided review story and canvas framing

- Reuse `stories` and `story_scenes`; do not create a parallel review-tour data model. Add a bounded story kind/link so one review story belongs to exactly one change set and each scene belongs to exactly one object change.
- Generate scenes server-side in stable object-change order. Each scene stores the affected object ID, before/after target bounds, deterministic camera framing with safe padding, and the object-change reference. Explanations and action validity remain authoritative in review tables rather than duplicated into narration text.
- For edited and added objects, frame the current object and highlight the AI-affected fields without relying on color alone. For a tentatively deleted object, frame the recorded before-state bounds and render an explicit non-interactive deletion placeholder until its decision is complete.
- Add a Review entry to the existing shared panel host plus a **Review changes** link in the originating AI comment reply. The panel shows change-set progress, step number, object identity/type, what changed, why, conflict/status text, and only the currently valid Keep, Request revision, and Discard actions.
- Playback is decision-paced: starting review frames the first unresolved scene, a terminal action advances to the next unresolved scene, and completed scenes remain reachable with Previous/Next. Manual canvas exploration pauses the review framing; Resume returns to the active scene target.
- Use the existing viewport/canvas geometry helpers and `motion` dependency for interruptible framing. Respect `prefers-reduced-motion` with an immediate or short non-sweeping transition, restore focus after panel actions, preserve keyboard control, and keep the current canvas visible if a scene target becomes unavailable.
- Realtime review invalidation contains only canvas/change-set identifiers. PostgreSQL remains authoritative after missed or repeated events; canvas changes continue to converge through durable Yjs updates and sequenced Broadcast.

### Failure behavior, observability, and deployment

- Keep local, deploy-preview, and production configuration distinct. No new provider credential, production AI enablement, production migration, or production deployment is authorized by this plan.
- Keep the last valid canvas and review projection visible during activation, decision, revision, story, collaboration, or refetch failure. Disable only the affected action and expose a readable retry when safe.
- Record privacy-safe activation/decision/story/visual-feedback telemetry: change-set and object-change IDs, requester/reviewer IDs, role/authority snapshot, expected and resulting durable sequence, decision, affected/conflicted field paths, story/scene IDs, capture kind/dimensions/byte count, deterministic check outcomes, feedback-pass count, outcome, latency, and error code. Do not record capture image content, canvas text, explanation bodies in operational logs, raw Yjs bytes, hidden reasoning, secrets, or unredacted provider errors.
- Deploy only after the approved slices pass local checks. Use an immutable Git-backed Netlify deploy preview for the exact protected-CI commit and complete hosted verification in Codex's in-app browser by default, with a second authenticated context for collaboration and concurrency.
