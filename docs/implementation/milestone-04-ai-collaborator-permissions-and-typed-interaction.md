# Milestone 4 — AI collaborator, permissions, and typed interaction

Status: Approved for implementation

Master plan: [`thinking-canvas-implementation-plan.md`](../../thinking-canvas-implementation-plan.md)

Plan owner: Product owner

Last updated: 2026-08-24

## Goal and user-visible outcome

Turn the Milestone 0 AI feasibility harness and Milestone 3 preview/test AI provenance into one permission-aware primary AI collaborator for each canvas, using the existing comment system as the only human/AI communication surface.

When this milestone is complete, the primary AI appears as a clearly identified collaborator alongside human participants. A participant communicates with it only through the same anchored, group-targeted, or world-space comment threads used with people. Typing `@` in an existing root-comment or reply composer opens one collaborator picker containing current human collaborators and the enabled primary AI. That explicit address establishes the thread's active conversation participants, so following comments continue to address the other active participants without requiring `@` on every turn. Using `@` again replaces the active addressed participant set from that turn forward without rewriting earlier history. When the primary AI is an active recipient of a human-authored turn, it can answer about the full canvas or an ordered connected path, respond as an ordinary AI-authored comment or reply, and expose cancel or retry inline. The same inheritance and redirection behavior applies to human-to-human conversations. There is no dedicated AI chatbot panel, AI chat composer, or parallel conversation history.

The AI can inspect off-screen content without relying on the current viewport, create or reply to contextual comments that point to its evidence, and use the same validated object vocabulary as a human when the current canvas AI authority permits it. A canvas-wide exchange begins as an existing world-space comment; an object or group exchange uses the existing anchored thread. AI proposals, review-staged changes, trusted edits, errors, and completion summaries return to the originating comment thread rather than creating a second workflow.

Resolving a comment conversation ends that conversation, rejects further replies or edits, closes its contextual card, and removes its marker from the canvas without deleting its history. Resolved threads remain available through comment history and remain eligible AI context alongside open threads. Permanently deleting a comment conversation removes the entire thread from product history and from every future AI context projection; provider storage and audit metadata must not preserve recoverable deleted conversation content.

The server re-checks the requesting human's membership and the current canvas AI authority before every provider request and again before every durable tool execution. Comment-only, proposal, review-staged, and trusted-edit authority levels expose different server-enforced tool sets. Canvas and comment text remain untrusted data and cannot add tools, change authority, or override developer instructions.

Milestone 4 establishes typed interaction inside comments, grounded evaluation, permission enforcement, and safe command execution. It does not deliver Milestone 5's per-object explanations, keep/revise/discard review UI, immediate restoration workflow, or guided review story.

## Requirements covered

This plan covers these exact Milestone 4 requirements and supporting items from the master ledger:

- **FR-015 — One primary AI.** Every canvas can enable one clearly identified primary AI collaborator in the first version.
- **FR-016 — Full-canvas inspection.** With permission, the AI receives a complete semantic canvas projection, including off-screen objects, within documented context-size safeguards.
- **FR-017 — Connected-path inspection.** A user can select a connected path or ordered sequence and ask the AI to interpret that exact selection in order.
- **FR-018 — Shared visual vocabulary.** The AI can create and edit every supported human canvas object through validated domain tools, subject to permission.
- **FR-019 — AI contextual comments.** The AI can attach a comment to the specific object or group supporting its observation.
- **FR-020 — Constructive challenge.** Evaluation fixtures demonstrate grounded questions or alternatives for weak assumptions, gaps, ambiguities, and clearer framings.
- **FR-021 — No empty praise.** Evaluation fixtures reject responses that substitute unsupported praise for substantive canvas-grounded feedback.
- **FR-022 — Adjustable authority.** A user can select comment only, propose changes, edit with review, or trusted editor, and server-side enforcement blocks every disallowed mutation.
- **Supporting work:** implement typed messaging that remains available independently of voice.
- **Supporting work:** let `@` establish one or more active human or AI conversation participants for a comment thread, inherit that routing on following turns, and redirect later turns while preserving prior history.
- **Supporting work:** make Resolve end the conversation and remove its canvas marker while preserving the complete thread for authorized history and AI context; permanently deleted threads are unavailable to future AI context.
- **Supporting work:** build a deterministic canvas-to-AI projection with object IDs, types, text, geometry, relationships, document summaries, and selected-path order.
- **Supporting work:** bound AI context by relevance without hiding the fact that off-screen canvas content exists.
- **Supporting work:** validate every AI tool call with Zod and re-check current membership and AI permission server-side at execution time.
- **Supporting work:** store AI request identifiers, tool decisions, affected object IDs, outcome, and failure status without storing secret credentials.
- **Supporting work:** add rate limits, budget limits, cancellation, timeout handling, and a visible retry path.
- **Supporting work:** treat canvas and comment content as untrusted input; prompt text cannot grant tools or permissions.
- **Exit gate:** “Evaluation suite passes groundedness, permission, malformed-tool-call, prompt-injection, and cancellation cases at the approved threshold.”

Milestone 4 preserves closed Milestones 1–3. It may populate pending `ai_change_sets` and `ai_object_changes` as a safe review-mode staging boundary, but it does not complete `FR-031` through `FR-035`, `AS-002`, or `AS-005`.

## Technical approach

### Delivery prerequisite and branch boundary

- Base implementation on merged `main` commit `bf8f3c6` from PR [#8](https://github.com/jewilhel/Thinking-Canvas/pull/8), protected CI run `32764955133`, and immutable Milestone 3 Netlify deploy `6a8c93460c7d4a72b34f8f05`.
- The local `main` and this planning branch both point to `bf8f3c6`. The closed Milestone 3 baseline passes on that merged tree: `pnpm check`, clean migration replay, all `161` direct local pgTAP assertions, and all `37` Chromium/accessibility scenarios.
- Drafting or approving this plan does not authorize Milestone 4 product implementation, pull-request creation, production changes, provider configuration changes, or master-ledger completion changes.

### Next.js, server, and provider boundaries

- Keep `/app/canvases/[canvasId]` as the authenticated Server Component and preserve its nondisclosing canvas authorization behavior.
- Add server-only AI data-access and execution modules marked with `server-only`. They re-authenticate, authorize, and return minimal DTOs; OpenAI keys, service-role credentials, provider request objects, and raw database rows never cross the Client Component boundary.
- Use uncached Next.js Route Handlers for comment-triggered AI runs, cancellation, settings changes, and server-authorized tool execution. Stream incremental AI reply text and status into the open comment thread without turning the canvas route into a client-owned security boundary.
- Use the OpenAI Responses API with custom function tools, strict JSON schemas, an explicit tool allowlist derived from current authority, bounded output, a privacy-preserving safety identifier, and server-side validation after the model returns a tool call. Set `store: false`; the existing Thinking Canvas comment thread is the visible conversation source of truth and separate AI-chat history is prohibited.
- Treat provider output as a proposal until it passes schema validation, current-object checks, current membership, current authority, idempotency, and command execution. The model receives no Supabase credentials and cannot call persistence directly.

### Primary AI identity inside the comment system

- Model one primary logical AI identity per canvas. It is visibly labeled as the primary AI in the collaborator identity treatment, AI-authored comments and replies, pending change sets, and audit records. Do not represent provider connectivity as human Presence or imply that the AI is continuously online.
- Keep the authenticated human requester as the accountable principal for each run and tool execution. Store the logical AI actor separately, reusing Milestone 3's provenance principle rather than impersonating a database user.
- Use the existing Comments panel, contextual thread card, root-comment composer, reply composer, markers, anchoring, ordering, lifecycle, hide/show, and collaborator refresh behavior. Do not add an AI panel, chatbot route, global chat drawer, AI-only composer, or separate AI conversation list.
- Typing `@` in either existing composer opens one searchable collaborator picker containing current canvas human collaborators plus the primary AI when it is enabled and the author may invoke it. The picker is keyboard-operable, uses combobox/listbox semantics, announces results and selections, supports removable recipient chips, restores focus predictably, and does not rely on color.
- Treat `@` as a durable conversation-routing change, not a text-only mention or permanent thread assignee. An explicit selection sets the active participant set to the submitting author plus the selected collaborators. A following turn without `@` inherits that set and is effectively addressed to every other active participant. A later explicit selection replaces the active set from that turn forward. An undirected thread remains possible until its first explicit address.
- Persist stable structured effective recipients for every submitted turn separately from the visible body, including whether they were `explicit` or `inherited`; do not infer routing by parsing display text. Preserve those recipient records when the active set later changes. Render a clear `To` treatment on each directed turn and show the inherited active recipients in the composer before submission so the author can redirect them deliberately.
- Only an authenticated human-authored turn whose effective recipients include the enabled primary AI creates exactly one idempotent AI run. An AI-authored response does not recursively invoke itself. Human-only or undirected conversations create no AI run.
- Keep the active participant set unchanged when the AI replies, so the next human reply continues to address the AI without another `@`. In a human conversation, each new turn is addressed to the other active participant or participants. If the AI creates a separately supported contextual comment, establish its active participant set from the accountable requester and relevant human co-participants while preserving linkage to the originating turn.
- A canvas-wide question is an existing world-space comment. A question about one object or selected group is an existing anchored comment. A connected-path request stores its ordered context on the AI run linked to the originating thread; it does not create a parallel message record.
- Persist visible human input and AI output only as `comments` and `comment_replies`, ordered by the existing deterministic thread contract. Store the current active participant set as routing state and each turn's immutable effective recipients in normalized relational metadata linked to those existing messages. Extend reply provenance where required so the primary AI is distinct and the requesting human remains accountable. Do not store hidden reasoning or secret provider payloads.
- Stream partial AI text and run status inside the open thread, then persist only the accepted user-visible AI comment or reply. Refresh collaborators through the existing low-frequency content-free comment invalidation event; PostgreSQL comments remain authoritative after reconnect or missed/repeated events.
- If the originating thread already targets the supporting object or group, reply there. If a full-canvas request yields a separately supported observation, the AI may create a new contextual comment through the same Milestone 3 command boundary and link its run back to the originating thread.
- Resolve is a terminal conversation action: after the status transaction succeeds, close the contextual card and omit that thread from the canvas-marker render set in every session. Keep the thread queryable in authorized comment history and visibly labeled `resolved`; do not permit inherited routing, replies, edits, prompts, or AI runs to continue in it.
- Permanent deletion keeps the existing irreversible confirmation and author/owner authorization boundary. After deletion succeeds, close the card, remove the marker and history entry, and exclude the thread and all cascaded replies/prompts/responses/routing records from every future AI projection.

### Deterministic full-canvas and connected-path projection

- Load the authorized canonical canvas from the latest durable snapshot plus subsequent updates; do not build the provider projection from viewport-visible Konva nodes or unacknowledged browser-only presentation state.
- Produce a versioned deterministic semantic projection containing every durable object's stable ID, type, content summary, geometry, group/order metadata, and relationships. Include comment/thread summaries only when the request and authority require them.
- Make authorized `open` and `resolved` comment conversations an available context corpus for every AI run. Include a complete deterministic thread manifest with status, stable thread/target IDs, participants, timestamps, and bounded summaries; provide a read-only `inspect_comment_threads` tool that pages the full visible root, replies, prompts, and responses when detail cannot fit inline. Marker visibility never controls context eligibility.
- Exclude `dismissed` and permanently deleted threads from the manifest and detail tool. Query the current relational comment tables at projection time so deletion takes effect immediately; never reconstruct deleted text from AI run metadata, logs, provider state, embeddings, caches, or stale projections. A run already in progress must revalidate referenced thread existence before persisting a response or tool result.
- Always include a complete canvas manifest so off-screen objects are never silently omitted. For a canvas that exceeds the approved request budget, keep the complete compact manifest and expose deterministic, server-paged detail retrieval through a read-only `inspect_canvas_objects` tool. Reject the request with a visible size-limit explanation if even the manifest cannot fit; never pretend the visible subset is the full canvas.
- Track exact serialized bytes, estimated/input tokens when available, object count, selected-detail count, truncation decisions, and projection version in privacy-safe test telemetry.
- Represent an ordered selection as stable object IDs in the user's selection order. For connected-path mode, validate that consecutive objects are connected by durable connector relationships; reject stale, cross-canvas, missing, or ambiguous input rather than silently reordering it.
- Include explicit viewport metadata only as optional user context. It must not govern which canvas content the AI is permitted to know exists.

### Authority-aware tools and command execution

- Define one strict tool registry whose schemas map to existing product commands and Milestone 3 comment commands. Required tools cover creating, patching, moving, resizing, styling, reordering, grouping, ungrouping, duplicating, deleting, attaching connector endpoints, creating contextual comments, inspecting canvas detail, and recording non-mutating proposals.
- Do not expose tools that bypass human capabilities or validated command invariants. Tool descriptions must state side effects, valid object types, retry behavior, and error results.
- Derive the provider `tool_choice` allowlist from the current persisted authority. Recompute authority before each tool execution; do not trust the allowlist alone.
- `comment_only` can read authorized context and create an AI-authored contextual comment or reply in the originating thread. It cannot create object commands or change settings.
- `propose_changes` can return validated ordered command proposals and affected IDs as a reply, but cannot persist canvas updates or review records.
- `edit_with_review` can stage pending `ai_change_sets` and `ai_object_changes` with before/after state and affected fields, then add a thread reply summarizing the staged result. It cannot change canonical Yjs state or create review decisions in this milestone.
- `trusted_editor` converts each accepted tool call into an AI-origin product command, executes it against the latest durable Yjs document, persists the generated update idempotently, broadcasts the server-assigned sequence, and records a concise result reply in the originating thread. If current state conflicts with the tool's preconditions, fail safely and report the retry path in that thread.
- Use one run-level idempotency key and one stable command ID per tool call. Repeated provider events, client retries, or ambiguous persistence acknowledgements must not duplicate comments, replies, change sets, or canvas mutations.

### Grounding, prompt-injection resistance, and product behavior

- Separate developer instructions, the invoking comment/reply, deterministic projection, prior visible thread history, and tool results as distinct typed inputs. Label canvas text, comments, replies, and prior AI output as untrusted content that cannot define tools or authority.
- Require grounded answers to cite stable canvas object IDs internally and render human-readable object links/highlights inside the AI-authored comment or reply. Validate cited IDs against the current authorized projection before persisting the response.
- For constructive-challenge fixtures, require at least one evidence-linked question, alternative, missing assumption, ambiguity, or clearer framing when the fixture contains a documented weakness. Do not require criticism when the evidence does not support it.
- Reject empty praise as the substantive answer. Brief acknowledgment may appear only when followed by canvas-grounded analysis that satisfies the rubric.
- Keep AI output visually distinct from human content without relying on color alone. Contextual AI comments reuse Milestone 3 thread, target, permission, and history behavior.

### Rate limits, budgets, cancellation, failures, and observability

- Enforce authenticated per-user and per-canvas request windows before provider access, plus input bytes/tokens, output-token, tool-call, object-count, run-duration, and per-run command-count limits. Keep numeric defaults server-configured and testable; record the approved hosted values without secrets.
- Show explicit `queued`, `projecting`, `thinking`, `tool_pending`, `applying`, `completed`, `cancelled`, and `failed` states inline in the originating thread. Keep the last valid canvas and complete thread visible throughout.
- Put Cancel and Retry in the pending/failed AI reply treatment inside that thread. Tie Cancel to an abort signal for the provider stream and a persisted run cancellation flag. After cancellation, discard late provider events and block all not-yet-started tool execution. A command already durably acknowledged is reported honestly in the thread rather than falsely rolled back.
- Apply bounded timeouts to projection, provider response, and tool execution separately. A retry creates or reuses idempotency keys according to the failure stage and never silently duplicates side effects.
- Store provider request ID, selected model, authority snapshot, projection version/count/size, tool name, affected object IDs, outcome, latency, token usage when returned, error code, cancellation time, and requesting principal. Do not store API keys, authorization headers, hidden reasoning, raw tool arguments containing canvas text, or unredacted provider errors.
- Keep local, preview, and production configuration distinct. No production AI enablement or credential change is authorized in this milestone.

## Database and security changes

After the open decisions are approved, create forward-safe additive migrations for:

- `canvas_ai_settings`: one row per canvas with enabled state, the four authority levels, version, changed-by principal, and timestamps. Apply the approved `PD-006` owner matrix in RLS and a fixed-search-path mutation function.
- Existing comments/replies: add only the provenance and linkage fields or transactional functions needed for an AI-authored root comment or reply to retain the logical primary-AI identity and accountable human requester. Preserve the existing thread ordering, lifecycle, target, and visibility contracts.
- `comment_thread_participants`: the current active human/AI participant set for each root thread, routing version, the message that last changed it through explicit `@` addressing, and timestamps. An explicit address transaction replaces this set with the author plus selected collaborators; an unaddressed reply inherits it without rewriting the set.
- `comment_message_recipients`: immutable effective recipients for each turn, linked to a root `comment_id` and, for replies, its `reply_id`; recipient kind (`human` or `ai`); exactly one stable human user ID or primary-AI key; routing version; source (`explicit` or `inherited`); and creation metadata. Enforce that the reply belongs to the linked root, each recipient appears at most once per message, and one valid message may have multiple recipients. A null `reply_id` addresses the root comment.
- `ai_runs`: originating root comment and invoking reply linkage, optional output comment/reply linkage, provider request ID, model, authority snapshot, ordered context IDs, projection metadata, status, timestamps, token/latency counters, cancellation, and privacy-safe error code.
- `ai_tool_executions`: run/call linkage, tool name, affected object IDs, outcome, command ID or comment/change-set reference, and timestamps without raw secret or content-bearing arguments.
- Rate/budget counters or transactional functions sufficient to enforce the approved per-user/per-canvas windows without client trust.
- Existing `ai_change_sets` and `ai_object_changes`: only additive fields or transactional functions needed to stage `edit_with_review` output idempotently without applying canonical canvas state. Do not implement review decisions or change-application behavior.

Preserve the existing hard-delete cascade from a root comment through replies, targets, prompts, and responses, and extend it to Milestone 4 routing records. AI run/tool audit rows may retain only privacy-safe operational facts after a source thread is deleted; any foreign key must clear or cascade, and no body, summary, prompt, response, recipient display snapshot, embedding, cached projection, or provider conversation state may remain recoverable from those rows.

For all new or revised records and functions:

- Enable RLS before application access; viewers may read only the visibility approved by the product owner and cannot invoke the AI. Owner/editor/commenter behavior follows the approved authority matrix.
- Re-check current membership and `canvas_ai_settings` inside trusted transactional functions immediately before each durable operation. Removed members and stale authority snapshots fail closed.
- Resolve explicit and inherited participant IDs from current canvas membership inside the submit transaction. Reject duplicates, nonexistent or cross-canvas users, removed members, forged AI keys, and a disabled or unauthorized primary-AI participant. If an inherited participant is no longer valid, fail visibly and require redirection instead of silently dropping or invoking that recipient. Preserve a former collaborator's historical recipient identity, but do not allow it in new routing.
- Resolve routing state, persist the root comment or reply and its immutable effective recipients, replace active participants when `@` is explicit, and create any AI run in one atomic transaction. Trigger from structured effective-recipient rows, never parsed text. A human-authored message effectively addressed to the primary AI may create exactly one run under one idempotency key; AI-authored output never recursively triggers another run.
- Use fixed search paths, explicit grants, strict JSON/array validation, UUID ownership checks, finite size limits, and canvas-scoped foreign keys or helper checks.
- Keep OpenAI access server-only. A service-role credential, if required for logical AI writes, must remain in server/Functions scope; every use must carry and verify the accountable human principal and selected authority.
- Regenerate `src/lib/supabase/database.types.ts` from a clean migrated local database.
- Add pgTAP coverage for owner, editor, commenter, viewer, non-member, unauthenticated, removed-member, settings ownership, authority downgrade during a run, thread isolation, explicit and inherited human/AI routing, routing replacement, immutable earlier recipients, resolved-thread terminal behavior and retained reads, hard-delete cascades, deleted-thread projection denial, reply-to-root integrity, duplicate/forged/stale/cross-canvas participant denial, exactly-once non-recursive AI invocation, AI reply visibility/provenance, exact retry/collision, rate limit, trusted mutation, comment-only denial, proposal non-mutation, review staging non-mutation, cancellation, and cross-canvas denial.
- Record retention implications: AI-authored comments/replies and audit metadata persist in non-production Supabase for milestone evidence under the existing comment-history contract; production launch remains blocked on the retention/deletion policy in Milestone 11. Set provider `store: false` and do not depend on provider-side conversation storage.

Rollback or compensation: disable AI invocation and settings mutation while retaining RLS-protected comment/thread and audit reads; preserve staged change sets and acknowledged canvas updates; ship additive grants/function corrections. Do not delete user canvases, comments, replies, or change records as rollback behavior.
